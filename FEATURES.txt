A1. STACK AND SHAPE
--------------------------------------------------------------------------------
  * npm workspaces monorepo: packages/shared, packages/server, packages/web, infra
  * React 18 + Vite 6 + react-router 6 + recharts (client, port 5173)
  * Express 4 + Zod + Node 22 (API, port 4000), bundled by tsup

A3. FINANCIAL ENGINE (packages/shared)
--------------------------------------------------------------------------------
  math.ts
    monthlyRate (geometric), annuityFactor, steppedAnnuityFactor (linear in the
    contribution, which makes the solver exact rather than an iterative search),
    futureValueLumpSum, requiredMonthlyContribution (closed form),
    solveRequiredReturn (bisection, returns null past 40%/yr),
    accumulate (shared by goals and retirement so a crash is modelled identically),
    createRng (mulberry32, seeded and reproducible), createNormalSampler
    (Box-Muller), percentile (linear interpolation), monthsToPayoff (Infinity when
    the payment does not cover interest), emiFor, clamp, sum, round

  portfolio.ts
    emptyWeights, holdingValue, correlationOf (order-tolerant),
    portfolioExpectedReturn, portfolioVolatility (full covariance including cross
    terms, so the negative equity/gold correlation actually lowers total risk),
    normaliseWeights, weightsFromHoldings, recommendAllocation (glide path:
    de-risks as the horizon shortens; under 3 years equity is cut hard regardless
    of appetite), concentrationIndex (HHI), analyzePortfolio

  risk.ts
    scoreRisk - separate tolerance (behavioural) and capacity (structural) scores,
    effective score = min(the two), bucket + human-readable drivers

  goals.ts
    yearsToGoal, projectGoal - reports the gap three ways (monthly top-up,
    required return, absolute shortfall)

  montecarlo.ts
    runMonteCarlo - seeded and reproducible; percentile bands per year, success
    probability, terminal-value histogram, variance-drag correction

  cashflow.ts
    totalMonthlyExpenses, summariseCashflow (savings rate, EMI load,
    debt-to-income, emergency cover/target/gap, expense breakdown),
    summariseNetWorth, assessRetirement (year-by-year drawdown at a de-risked
    post-retirement return to find the actual depletion age, and it publishes the
    exact plan inputs so a Monte Carlo simulates the SAME plan),
    planDebtPayoff (avalanche vs snowball + unpayable debts),
    scoreWellness (5 published pillars with fixed weights, plus a dataComplete
    flag so an empty profile is reported as incomplete rather than graded C)

  engine.ts
    resolveAssumptions (user overrides layered on the house view), planningHorizon,
    returnForGoal (per-goal return by that goal's own horizon, not one blended
    number), buildSnapshot (single pass producing everything the dashboard needs),
    runScenario (absolute outcome + delta vs baseline), describeLevers,
    SCENARIO_PRESETS

  assumptions.ts
    6 asset classes, DEFAULT_ASSUMPTIONS (6% inflation, 6.6% risk-free, per-class
    returns and vols, 15 correlation pairs, 3.5% SWR, 6 months emergency),
    5 MODEL_PORTFOLIOS, 6 RISK_QUESTIONS (3 tolerance + 3 capacity), FX + currency meta

  format.ts
    Indian L/Cr abbreviations for INR and K/M/B for USD, currency, percent, number,
    years and signed-delta formatters, illustrative FX conversion

  data/personas.ts
    3 synthetic personas, each illustrating a different planning problem:
      Aarav, 26  - good income, no buffer, expensive card debt
      Meera, 38  - competing goals, home loan, under-insured
      Rohan, 52  - eight years out, portfolio too aggressive, one big position

A4. THE AGENT (packages/server/src/agent)
--------------------------------------------------------------------------------
  Workflow: PLAN -> ACT -> SYNTHESIZE -> VERIFY, every phase narrated over SSE.
  A hand-written loop rather than the SDK tool runner, because each phase has to be
  streamed to the client and the plan revised as tools return.

  Core guarantee: the model narrates, it never calculates. Every figure comes from
  a tool result, and the verifier re-checks each number in the prose against the
  tool outputs. Unmatched figures are reported as unverified, not trusted.

  14 tools, each returning summary (for the trace) + data (for UI cards) +
  facts (for the verifier):
    get_financial_snapshot, project_goal, simulate_scenario, run_monte_carlo,
    analyze_portfolio, recommend_allocation, get_next_best_actions,
    estimate_action_impact, optimise_goal_funding, plan_debt_payoff,
    compare_scenarios, search_knowledge, update_plan, list_scenario_presets

  intent.ts       10 intents (overview, goal, whatif, portfolio, actions, debt,
                  probability, education, update, compare) via phrase/word scoring.
                  It IS the planner in deterministic mode, and the instant
                  first-paint plan plus LLM fallback otherwise.
  knowledge/      14-document planning corpus with BM25 retrieval and a light
                  stemmer. Lexical on purpose: no model call, no vector store,
                  works with zero credentials.
  llm.ts          One interface over Bedrock / Anthropic API / none. Bedrock uses
                  the Lambda execution role, so no API key exists in the system.
  synthesis.ts    Template synthesiser for the no-credentials path - every
                  sentence is built from a tool result, so it passes the same
                  grounding verifier the model's answers go through.
  verifier.ts     Extracts currency/percent/duration claims (Cr/L/k/M/B aware),
                  matches them against tool facts, returns grounded/unverified
                  with evidence. Deliberately conservative about bare integers.
  orchestrator.ts System prompt with 5 absolute rules (never calculate, always
                  read the position first, make assumptions visible, never claim
                  market certainty, no product or security recommendations),
                  answer-style rules, step ceiling, abort support.

A6. DATA, PERSISTENCE AND RUN MODES
--------------------------------------------------------------------------------
  * Store interface with two implementations: MemoryStore (local/tests) and
    DynamoStore (single table, pk=PROFILE#id, sk=meta | SESSION#id, GSI for
    listing so it never scans)
  * The client persists only the profile id in localStorage; the snapshot is
    computed locally from the profile by the shared engine, so every edit is
    instant and the server is authoritative for persistence, not for display
  * Four run modes selected by environment, no code change:
      deterministic - no credentials at all, full feature set, rule-based prose
      anthropic     - ANTHROPIC_API_KEY set (wins if several are available)
      groq          - GROQ_API_KEY set
      bedrock       - AWS region + Lambda execution role
  * Tunables: PORT, NODE_ENV, LOG_LEVEL, CLAUDE_MODEL, MAX_AGENT_STEPS (6),
    SIMULATION_PATHS (2000), REQUEST_TIMEOUT_MS, CORS_ORIGINS, TABLE_NAME,
    GROQ_MODEL, GROQ_MAX_TOKENS, GROQ_RETRY_BUDGET_MS, GROQ_BASE_URL
  * npm run dev loads a .env at the repo root if one is present
    (--env-file-if-exists); npm test deliberately does not, so the suite stays
    on the credential-free path

A10. ADDED SINCE THIS FILE WAS FIRST GENERATED
--------------------------------------------------------------------------------
  A1-A9 above have been corrected to match. This section covers only what is
  new, and why it exists. Read from the source, same as the rest of the file.

  A10.1  HEALTH COVER AS A FIRST-CLASS NEED
    - healthCoverTarget() in assumptions.ts:
        max(annual income x multiple, floor for age band) + per-dependent loading
      The max is the model: income alone under-insures a young earner whose
      first admission costs what anyone else's does, and a flat floor alone
      under-insures a high earner whose household spends more when treatment
      interrupts earnings.
    - HEALTH_COVER_AGE_BANDS (40 / 55) step the floor rather than scaling it,
      because treatment cost rises with age while insurability falls.
    - close-health-cover-gap is rule 5 in the waterfall, between the two cover
      rules. It states the shortfall and the target it was measured against.
    - The wellness Protection pillar scores against that same target, so the
      score and the action can no longer disagree.
    - All five constants are editable in the Assumptions ledger.

  A10.2  WHAT THE PLAN IS WORTH  (Dashboard hero)
    - GET /api/plan/:id/impact returns before/after for the top N actions:
      wellness score and grade, retirement funded %, goals on track, total
      interest paid, months to debt-free, median corpus, emergency months and
      monthly surplus, plus each action's marginal contribution.
    - components/ImpactHero.tsx renders it at the top of the Dashboard.
    - Computed server-side: three cumulative snapshots and three seeded
      simulations are not work for the render thread. Refetched on save.
    - Only applicable, affordable actions count, so the figure cannot promise a
      contribution the household cannot fund.
    - Negative marginals are shown, not hidden: raising equity can raise the
      expected return and the variance drag together, lowering the median.

  A10.3  GOAL-PRIORITY OPTIMISER  (Goals)
    - shared/optimiser.ts: allocateSurplus() and optimiseGoalFunding() decide
      which goals get the one surplus when they compete, scoring on priority
      weight, funded ratio and time remaining.
    - A goal inside nearTermGoalMonths of its date funds before longer-horizon
      goals of equal priority: a near-term goal cannot be rescued later and has
      no compounding left to make up the difference.
    - components/SurplusSplit.tsx makes the cost as prominent as the
      recommendation. Every starved goal states its delay in years, because
      "your second home arrives four years later" is a sentence someone can
      decide about and "short by 41 lakh" is not.
    - POST /api/plan/:id/optimise-goals; optimise_goal_funding is an agent tool.
    - Four new ledger tunables: goalWeightMustHave, goalWeightImportant,
      goalWeightAspirational, nearTermGoalMonths.

  A10.4  CONVERSATION HISTORY, SHARED BASELINE, RISK LADDER
    - GET /api/agent/:id/sessions and GET /api/agent/sessions/:sessionId back a
      conversation list in the Assistant, so a session survives a reload.
    - components/RiskLadder.tsx appears on both Portfolio and Assumptions,
      driven by useRiskLadder(profileId).
    - Scenario comparison runs against a shared baseline rather than per-card
      baselines, so two scenarios are read from the same starting point.

  A10.5  GROQ AS A FOURTH REASONING PROVIDER
    - agent/groq.ts is a pure translation layer between Anthropic message shapes
      and Groq's OpenAI-compatible Chat Completions endpoint, in both
      directions, handing back a real Anthropic.Message. The orchestrator is
      untouched and still has no provider branching.
    - No new dependency: Groq's wire format is JSON over fetch, so the Lambda
      bundle is unchanged at 271 KB. Default model openai/gpt-oss-120b.
    - reasoning_effort is sent by allowlist (gpt-oss, qwen3). groq/compound
      rejects the parameter with a 400, so an unknown model loses effort control
      rather than losing the whole request.
    - gpt-oss streams its chain of thought in a `reasoning` field beside
      `content`. Only `content` is forwarded, because whatever is forwarded is
      streamed into the user's answer.
    - GROQ_MAX_TOKENS (1500) clamps the orchestrator's 8000. Groq reserves the
      whole of max_tokens against a per-minute allowance, so passing 8000
      through spends a free account's entire minute on one call, and every
      request 429s before the model sees it.
    - Two retries, honouring the wait Groq states in the 429 body and the
      retry-after header, bounded by GROQ_RETRY_BUDGET_MS (12s) across the whole
      call. This matches the maxRetries: 2 the Anthropic SDK gives the other
      paths; without it the Groq path was the least resilient of the four.
    - activeModel() in config.ts: /api/health and /api/agent/capabilities report
      the model actually answering. They returned the Claude id for any
      non-deterministic provider, so Groq mode badged the UI claude-opus-5 while
      gpt-oss did the writing.
    - Quota behaviour, not a defect: an agent step costs ~3,000 tokens with all
      14 tool schemas attached, against 8,000/minute on a free Groq account -
      about two steps. Past that the run falls back to the deterministic engine
      and the answer arrives with identical numbers, in plainer prose.

  A10.6  SSE: A RECOVERABLE AGENT ERROR NO LONGER KILLS THE STREAM
    - `error` is unusable as an SSE event name. EventSource dispatches a server
      frame of that name as the same event a dropped connection fires, so the
      browser client read a recoverable agent notice as a dead socket, closed
      the stream, and discarded the `final` answer arriving milliseconds later.
      The symptom was "The connection to the assistant was interrupted" on runs
      the server had completed successfully.
    - SseStream maps that one event to `agent_error` on the wire. The payload
      still carries type: 'error', so AgentEvent in @wealth/shared and every
      consumer switching on event.type are unchanged.
    - Latent since the first agent build; only reachable once a provider began
      failing mid-run.

  A10.7  THE ENGINE IS CURRENCY-CORRECT, NOT JUST THE FORMATTER
    - Four assumptions are amounts of rupees rather than rates: the three health
      cover floors and the per-dependent loading. Nothing converted them, so a
      USD profile was measured against unconverted rupee constants - a 5,00,000
      rupee floor read as $500,000, and every user looked uninsured. Measured
      before the fix: Protection 28->11 (aarav), 56->46 (meera), 75->60 (rohan),
      with every other pillar unchanged.
    - MONETARY_ASSUMPTION_KEYS names those four; ASSUMPTION_BASE_CURRENCY
      records that the house view is stated in INR.
    - resolveAssumptions() - the one chokepoint every consumer already goes
      through - restates them in the profile's currency, which fixed the engine,
      the optimiser, the agent tools and the server at once.
    - Overrides are stored in the profile's currency and layered on after
      conversion: the ledger edits in the displayed currency, so converting an
      override again would divide the user's own number by the rate twice.
      switchCurrency moves them along with every other amount.
    - Ledger slider bounds are currency-aware. Written in rupees they are 83x
      too coarse to express a converted value, so touching a slider in USD would
      have snapped the assumption to something absurd - a display bug becoming a
      data-loss bug.
    - Residual: switchCurrency rounds to whole units, so one pillar of one
      persona can read +/-1 between currencies. Re-measured with an unrounded
      conversion it is identical, which is how we know it is rounding rather
      than another stray constant.

  A10.8  DEVELOPER-FACING
    - npm run dev loads a repo-root .env via --env-file-if-exists. Nothing read
      that file before, so .env.example was aspirational and a key set there did
      nothing. npm test deliberately does not load it, so the suite stays on the
      credential-free path.
    - New test files: shared/test/currency.test.ts (currency invariance across
      every persona), server/test/groq.test.ts (the wire mapping in both
      directions, stream-chunk reassembly, the retry policy) and
      server/test/sse.test.ts (the reserved event name never reaches the wire).
    - docs/DEPLOYMENT.md and .env.example document every GROQ_* tunable and the
      free-tier quota arithmetic.

PART B - DELIBERATELY NOT MODELLED (and said so in-app)
================================================================================
  * No taxes anywhere - no capital gains, dividend or income tax on any projection
  * No transaction costs - brokerage, exit loads, spreads, rebalancing costs
  * Thin tails - returns are log-normal and drawn independently; real markets
    crash harder, more often, and in clusters
  * Synthetic data only - no market feed, no account aggregation, no institution
  * Not advice - illustrative planning output, not a regulated recommendation

================================================================================
PART C - GAPS AND CANDIDATE NEXT WORK
================================================================================

C1. BLOCKERS FOR ANYTHING BEYOND A DEMO
  * NO AUTHENTICATION AT ALL. Any caller can list every profile
    (GET /api/profiles), then read, overwrite or delete any of them by id. The
    client just keeps a profile id in localStorage. Auth and per-user scoping are
    required before this is exposed publicly.
  * No rate limiting, no WAF, no request throttling. The agent endpoints call a
    paid model and run 2,000-path simulations; both are wide open.
  * No CloudWatch alarms or dashboards in the CDK stack - X-Ray tracing is on but
    nothing watches error rate, latency or Bedrock throttling.
  * DynamoDB has a ttl attribute configured but nothing ever writes it, so chat
    sessions accumulate forever.

C2. BUILT ON THE SERVER, NOT SURFACED IN THE UI  (cheapest wins)
  * [DONE - see A10.4] Chat history. The Assistant now lists conversations and
    reloads them; the endpoints it was always able to call are now called.
  * POST /api/plan/:id/scenarios/compare runs up to 6 scenarios server-side; the
    Scenario Lab pins a maximum of 3 and compares them client-side only.
  * [PARTLY DONE - see A10.4] The risk ladder (GET /api/plan/:id/allocation) is
    now on Portfolio and Assumptions. Scenarios still does not offer it.

C3. MISSING RULES AND MODEL FIDELITY
  * [DONE - see A10.1] healthInsuranceCover was collected everywhere and read
    nowhere. It now drives close-health-cover-gap and the Protection pillar.
  * [DONE - see A10.3] Goal-priority optimiser. shared/optimiser.ts allocates the
    one surplus across competing goals and names what the starved ones cost.
  * Retirement drawdown uses a single de-risked deterministic return to find the
    depletion age; sequence-of-returns risk is only modelled in accumulation.
  * use-tax-deduction checks remaining deductible room rather than computing an
    actual tax saving, because there is no tax model to compute it with.
  * Rebalance trades are shown gross - no exit load, no capital-gains consequence,
    which for a real portfolio can reverse the recommendation.

C4. PRODUCT SURFACE NOT YET BUILT
  * No export of any kind: no PDF plan, no CSV, no shareable scenario link.
  * Still no real multi-currency: one display toggle at a hardcoded 83 INR/USD
    rate, labelled illustrative in the UI. The engine is now currency-correct
    either side of that toggle (A10.7), but the rate itself is not live, there
    is no third currency, and no amount carries its own currency.
  * No account aggregation or market data - every price is user-entered.
  * No notifications, reminders, or progress-over-time tracking. The platform has
    no concept of history: no snapshots are stored over time, so "am I doing better
    than last quarter" cannot be answered at all.
  * No PWA/offline support, no mobile app.

C5. TESTING AND QUALITY
  * Web tests are SSR smoke renders only - no interaction tests (no slider drag,
    no Apply-to-my-plan click) and no end-to-end browser test.
  * No load test or cold-start measurement against the deployed Lambda.
  * No accessibility audit, though aria labels and chart/table toggles are present.
  * No error tracking or product analytics in the client.

C6. HOUSEKEEPING
  * README says "Thirteen rule checks"; the engine has 14 action rules.
  * scripts/ exists and is empty.
  * The project is not a git repository - no version control, so none of the CI
    workflows or the deploy pipeline can actually run yet. Worth fixing first if
    any of C1-C5 gets picked up.
